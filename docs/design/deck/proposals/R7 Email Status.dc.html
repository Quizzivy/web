When email stops reaching someone

R7 sends email in earnest: reminders, results, messages, weekly summaries. When a message bounces hard, or the person reports it as spam, the server stops sending to that address for good (T-R7.15). No screen says so. An admin who is asked why a student gets no reminders has nowhere to look, and the plan asks for a design (O-R7.3, DG-96). This page proposes one notice in the Admin user sheet, drawn with the product’s own callout. It adds no action, and it names what it would need from the server. R7’s plan does not build it; the last question asks when.

{{ c }}
Where it shows In the one place an admin already opens to ask about a person.
  • The Admin user sheet, first in its body, above the role. It is there only while the address is stopped; a sheet with nothing to report is the sheet of today.
  • It is the product’s warning callout, the one the data export and the password reset already use. No new part.
  • The Users list, the teacher’s Students and the person’s own Settings do not show it here. Each is a question below.
What it says What happened, since when, and what still works.
  • A bounce and a complaint read differently: one is an address that refuses mail, the other is a person who asked not to get it.
  • It claims no cause it cannot know. A hard bounce means the address refused the message; whether it is mistyped or closed, the server is not told.
  • In-app notifications are not touched, and the notice says so, so nobody thinks the person is cut off.
What it does not do No button: the way back is another address.
  • The list is kept by address. Give the account an address that works, and mail flows again with nothing else to do.
  • Nothing here sends to the stopped address again. Retrying a hard bounce harms the centre’s sending name, and writing to someone who reported spam goes against what they asked.
  • The Admin sheet has no action that changes an email today. That gap is the first question.
